## 2. Achados de segurança (do `supabase_lints`)

### 2.1 🔴 CRÍTICO — Dados sensíveis expostos via `anon` key

Confirmado pelo lint `sensitive_columns_exposed`:

| Tabela | Coluna sensível | Linhas afetadas |
| --- | --- | ---: |
| `chaves_api` | `secret_key` | 532 |
| `instancias_whatsapp` | `token` | 157 |
| `instagram_accounts` | `access_token` | 17 |
| `telegram_conexoes` | `session_string` (não taggeada pelo lint, mas equivalente) | 35 |

**Vetor de ataque:** o `anon` key pode estar no `.env` do frontend público, em commits no GitHub, no console do navegador. Qualquer pessoa com ele pode rodar `select * from chaves_api` e extrair as 532 chaves de afiliado dos 187 assinantes.

### 2.2 🔴 CRÍTICO — `bio_pages` e `bio_ofertas` têm policies sempre-verdadeiras

```
bio_ofertas_delete:  USING (true)
bio_ofertas_update:  USING (true) WITH CHECK (true)
bio_ofertas_insert:  WITH CHECK (true)
bio_pages_delete:    USING (true)
bio_pages_update:    USING (true) WITH CHECK (true)
bio_pages_insert:    WITH CHECK (true)
```

Como o usuário confirmou que bio_pages **é multi-tenant** (cada assinante edita só a sua), essas policies estão **incorretas em produção**: o assinante A consegue editar/deletar a bio do assinante B usando o `anon` key.

### 2.3 ⚠️ Funções sem `search_path` fixo

As 4 funções públicas têm `search_path` mutável. Risco baixo enquanto nenhuma for `SECURITY DEFINER`, mas é hardening barato (1 `ALTER FUNCTION` por função).

### 2.4 ⚠️ Auth pool fixo em 10 conexões

`auth_db_connections_absolute` — se o tier do Supabase for upgraded, o Auth não vai aproveitar. Trocar para percentage-based.

## 4. Achados estruturais (não-bloqueantes)

1. **Inconsistência de identificadores de usuário** entre subsistemas:
   - `usuarios.id` → `integer` (WhatsApp, assinaturas, chaves)
   - `telegram_*.wp_user_id` → `integer` (sem FK para `usuarios`!)
   - `bio_pages.user_id` → `text` (sem FK para `usuarios`)
   - `instagram_accounts.user_id` → `bigint` (sem FK)
   - É um débito técnico que dificulta queries cross-feature e impede CASCADE em delete.

2. **Tabela `cliques-link-whatsapp` com hífen no nome** — exige aspas duplas em todo SQL e quoting via REST. Renomear pra `cliques_link_whatsapp` em algum momento (com view de compatibilidade durante a transição).

3. **Timestamps inconsistentes**: a maioria das tabelas WhatsApp usa `timestamp without time zone` (perigoso em produção multi-região); as Telegram/bio usam `timestamptz` (correto). Padronizar pra `timestamptz`.

4. **`assinaturas.status` é `text` com default `'ativo'`** mas sem CHECK constraint. Vulnerável a valores inválidos.

5. **`disparos_log` tem 4 FKs sem dados** — provavelmente o n8n nunca chegou a popular essa tabela. Vale conferir se é morta ou planejada.
